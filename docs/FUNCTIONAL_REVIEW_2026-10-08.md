## 優先補強

### 1. 高：確認成團前未重新檢查外部日曆（已於本次後續修正上線）

位置：`supabase/functions/api/index.ts:1077`、`supabase/migrations/202610030009_confirm_and_calendar.sql:36`。

確認路由直接呼叫 `admin_confirm_group_event`，沒有先 `syncCalendar`。SQL 僅在延長場次時檢查 `calendar_busy`，而且只檢查新增的尾段；同長或縮短時不檢查外部忙碌。

情境：玩家開團後，店家另在 Google／Outlook 加入同時段行程，再確認成團。原鏡像可能已過期；即使鏡像更新，同長場次也沒有重查整段，因此可能接受撞期。

補充重現：合成 API 請求得到 201，確認 RPC 有呼叫，`sync_calendar_busy` 沒有呼叫。SQL 程式碼確認只檢查延長尾段。本次未在正式日曆製造撞期。

修正結果：0032 與 API 已上線，成團前同步完整實際時段，再由 SQL 檢查整段忙碌；查詢期間劇本時長改變會拒絕確認，已成團重送仍保持冪等。完整本機測試 107 項通過、精確部署版本成團／取消 API 測試 7 項通過、正式資料庫回滾驗收 PASS。仍需店家手機完成「開團後新增重疊行程 → 阻擋 → 移除後成團」實測。部署版本與本機會員效能差異詳見 PROGRESS。

### 2. 高：通知重試依賴下一次成功操作

位置：`supabase/functions/api/index.ts:1307`、`supabase/migrations/202610030011_notifications.sql:90`。

`deliverNotifications` 只在成功的非 hooks POST 之後觸發；每次預設處理 20 筆。SQL 記錄下次重試時間，卻不會自行喚醒發送。本機專案中未找到定時重送設定。

情境：最後一筆操作遇到 LINE 429／5xx 或網路失敗，之後只有玩家瀏覽或完全沒有操作，通知不會準時重送。一次超過 20 筆的通知也可能留下待送資料；一天後會被標成 STALE 而略過。

建議：增加受保護的通知處理入口與定時觸發，分批處理並限制執行時間；讓店家看到待送數、最老通知及失敗數。若正式環境已有外部排程，需另行核對，目前無證據可確認。

### 3. 高：新名字認領把過期名單當成有效查重來源

位置：`supabase/functions/api/index.ts:611`、`supabase/functions/api/index.ts:993`。

`POST /me/survey/name` 雖要求再讀最新名單，但 `playRecordSummary(settings, 0)` 在來源失敗時會回傳舊副本並標 `stale=true`。認領路由只看名字，不檢查 stale，仍可呼叫 `claim_record_name`。

補充重現：提供 10/1 的副本、現在時間 10/8，模擬 Apps Script 全部離線，認領仍回 201 並執行認領 RPC。

影響：副本更新後才加入的名字，可能被新玩家誤認領；之後問卷紀錄或點數可能歸錯人。既有「老玩家別名不在公開總覽」問題會造成另一種同名歸戶風險。

建議：會員卡顯示可以用舊副本；名字所有權查重則需最新且可信的結果，來源不可用時暫停取名。最好由 Apps Script 在同一個鎖內檢查正式名與別名並保留名字，避免查重與認領之間的競態。
