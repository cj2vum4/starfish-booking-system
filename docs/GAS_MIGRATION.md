# 移除 Google Apps Script（GAS）計畫

2026-10-11 店家決定：把網站的兩支 Apps Script（玩本記錄、角色問卷）全部搬進預約系統（Supabase），最後關掉 GAS。
盤點依據：兩個 repo 的完整程式碼閱讀（含 `GoogleAppsScript_玩本記錄.gs` 1606 行、`tests/gas.test.js`）。

## 第 2 階段設計

### 資料表（新 migration）
- `record_players`：歸戶名（唯一，另存正規化名稱：去空白、小寫）、探員編號（唯一，第一筆計點紀錄時給號）、加入日期、
  鍍金／自訂稱號／傳奇殿堂、備註。`player_bindings.record_name`、`line_record_accounts` 先維持以名字對應。
- `record_aliases`：別名（正規化）→ 玩家。
- `play_records`：送出時間（伺服器時間）、填寫的名字、歸戶玩家、劇本（reviewKey）、遊玩日期、角色、評價 1–5、心得（50 字）、
  介紹人（原文＋對到的玩家）、狀態（計點／重複／超過每日上限／補登逾期／作廢）、來源（網站／試算表匯入）、匯入去重鍵、
  舊表單多出來的「角色…」欄、精選、讚數。
- `point_ledger`（只增不改）：玩家、類型（記錄點數／介紹／任務／按讚／精選／回歸禮／兌換／補點扣點）、點數、明細、劇本、日期、
  月份、狀態（有效／作廢＋誰在何時為何作廢）、去重鍵（唯一）、對應紀錄、建立者。餘額＝有效點數加總。
- `point_settings`（17 個設定，型別化）、`quests`、`rewards`、`review_likes`（每則心得每個按讚者一次）。
- 第 3 階段：`redemption_requests`（玩家申請 → 店家核准／不通過 → 寫扣點帳本）。

### 計分（送出當下算好、寫進帳本後固定）
與現行 GAS 規則相同的數字與條件，差別只在「不再回頭重算」：
- 基本 10；心得（去掉空白後 ≥ 15 字）＋5；首玩（自己第一次玩這本）＋5；首探（全店第一筆這本）＋10；新手好運（自己第一筆）＋20；
  以上依「雙倍日」設定（送出當下的設定，以遊玩日期判斷）× 2。
- 重複（同人同本同日）、超過每日上限（3 筆）、補登逾期（送出日比遊玩日晚超過 7 天）：記錄但 0 點，不佔首玩／首探／新手好運。
- 介紹人：只在被介紹者第一筆計點紀錄給；被介紹者＋10、介紹人＋10，不加倍。
- 每月任務（場次 3／心得 2／新本 1／揪團 1）：達成當下發一次，之後不收回。
- 按讚：每讚 2 點、每則心得最多 10 點；精選＋20（店家按一次）。
- 回歸禮：店家核准綁定時在同一筆交易寫入帳本（不再呼叫 GAS、不再需要 `PLAY_RECORD_SECRET`）。

### 修掉的現有問題（盤點時找到）
- 「本月任務」進度月份格式對不上（可能一直顯示 0）。
- 表單送出後顯示的「+N 點」有時是上一筆的。
- 對不存在的心得按讚也加點、介紹人亂填也拿 10 點。
- 作廢某些列會被下次重算復原；作廢「重複」列會連帶作廢真正那筆。
- 同時送出沒有鎖，可能互相蓋掉。
- 公開 CSV 外露填寫時間、介紹人與舊流程的內部 ID：新的公開資料只給榮譽牆需要的欄位。

### 網站改動（切換日一起上線）
- `play-record.js` 送出 → `POST /public/play-records`；`reviews.js` 按讚 → `POST /public/likes`。
- `points.js`、`reviews.js`、`play-record.js` 讀點數 → `GET /public/records`（直接由 SQL 產生，JSON 格式與現在相同）。
- `榮譽牆.html`、`reviews.js` 原本讀 Google 發布的 CSV → `GET /public/play-records`。
- 拿掉 JSONP 與「先檢查 GAS 網址才讀 Supabase」的判斷。

### 匯入與切換
1. 部署新 migration 與 api（網站仍用 GAS，兩邊不衝突）。
2. 店家把「玩本記錄」試算表共用給服務帳戶（檢視者），在 LINE 店家畫面按「匯入玩本記錄」：
   表單回應 → `play_records`（保留原始時間戳記）；點數帳本 → `point_ledger`（照 GAS 已算好的點數原樣搬、固定）；
   玩家（別名、探員編號、加入日期、鍍金／稱號／傳奇）、設定、獎勵、任務、心得互動。
3. 對帳：每位玩家的餘額與 `play_record_snapshot`（GAS 最後一次的點數總覽）逐一比對，全部一致才切換。
4. 切換：網站改讀寫 Supabase。切換後若有舊頁面送到 GAS，再按一次匯入（以去重鍵只補新列，並用新規則計點）。
5. 觀察一段時間無誤 → 第 4 階段。

### 第 2 階段開工前請店家確認（我的建議）
1. 介紹人：只接受已存在的玩家名字（建議），亂填的不給點、只記錄。
2. 按讚：同一則心得、同一個瀏覽器只算一次（現況）；要不要改成必須 LINE 登入才能按讚（建議先維持現況）。
3. 作廢一筆玩本記錄：只作廢那筆的點數；它原本拿到的「首探／首玩」不轉給別人（建議，固定制下最單純）。
4. 首探：以「送出順序」決定（固定制下必然如此）；補登更早日期的紀錄不會搶走別人已拿到的首探。
